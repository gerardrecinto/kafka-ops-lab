The pipeline

  
The architecture from the README, one message at a time. Each exit is a separate topic so poison and retry traffic never compete with the main stream.

  
producer  (key: service or environment)
   |
   v
deploy-events  (6 partitions)
   |
   v   consumer group
   +-- schema validation ----- invalid ----------> deploy-events-dlq   (poison, never retried)
   +-- Redis dedup fast-path - already seen -----> skip write, commit offset
   +-- Postgres upsert ON CONFLICT DO NOTHING     source of truth for idempotency
   +-- transient failure ----> deploy-events-retry (retry_count header)
   |                              retry_count > 3 -> deploy-events-dlq
   +-- backpressure: slow sink -> consumer.pause() for a cooldown window

  
If Redis is wiped, correctness holds: every message just costs one extra Postgres round trip to find it already exists.

Run it yourself

  
Docker, Python 3.12.

  

    


docker compose up -d      # Kafka (KRaft), Postgres, Redis
python3.12 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt && pip install -e .

python -m kafka_ops_lab.admin
python scripts/smoke_test.py

    

    


python scripts/investigate_imbalance.py
python -m pytest tests/ -v

      
Single local broker, replication factor 1. A production setup would use 3.

    

  






  
What this does not do
    
    
  • It is a lab on one local broker. It makes no claim about production throughput.
    • 
    
  • The schema checker is a small stand-in for a real schema registry such as Confluent or AWS Glue.
    • 
    
  • Backpressure is a threshold and a fixed cooldown, not an adaptive controller.
    • 
    
  • This page cannot show lag monitoring, the retry topics or the Postgres sink, because they need the running services.
